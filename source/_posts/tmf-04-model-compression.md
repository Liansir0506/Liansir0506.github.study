> **一句话概括**：模型压缩 = 用更少的参数/精度/计算量，换回接近原模型的效果——让 BERT 能在线上以可接受的成本跑。
> **这篇有多重要**：🔥 —— 面试问"模型太大部署不了怎么办"的标准答案；也是"工程优化意识"的体现。
> **前置知识**：dl-05 的正则化、tmf-02 的 BERT 微调
> **对应素材**：`tmf/01课件/07-markdown/day05_模型压缩方法.md`

## 一、初识：为什么需要压缩

BERT-base：**1.1 亿参数**，FP32 存储约 440MB。

| 场景 | 问题 |
|---|---|
| 推理延迟 | 单条 100ms+，高并发扛不住 |
| 显存/内存 | 单模型几百 MB，多实例部署成本高 |
| 边缘设备 | 手机/嵌入式根本放不下 |
| 成本 | GPU 按小时计费，越大越贵 |

> 一句话：**效果好但跑不动的模型，业务价值是 0。**

## 二、初识：四种主流技术一览

| 技术 | 做什么 | 原理直觉 | 典型压缩率 | 精度损失 |
|---|---|---|---|---|
| **量化 Quantization** | 参数从 FP32 → INT8/INT4 | 数值精度降低（小数点后位数变少） | 4×（FP32→INT8） | 小（1~3%） |
| **剪枝 Pruning** | 删掉不重要的权重/神经元 | 去掉"贡献小"的连接 | 2~5× | 中（需重训微调） |
| **蒸馏 Distillation** | 大模型教小模型 | 小模型学大模型的输出分布（软标签） | 模型体量 1/10 | 小（可恢复 90%+） |
| **低秩分解 Low-Rank** | 大矩阵拆成两个小矩阵 | 权重矩阵存在"冗余方向" | 2~4× | 小~中 |

### 2.1 什么时候用哪种

```text
推理慢但模型不大？        → 量化（最省事，几乎无痛）
显存吃紧、可接受重训？     → 剪枝
要让小模型达到大模型效果？  → 蒸馏
矩阵维度大、想减少计算量？  → 低秩分解
```

> 📌 工程上常**组合使用**：蒸馏出小模型 → 量化到 INT8 → 少量剪枝 → 上 ONNX 推理。

## 三、初识：低秩分解（本项目采用的技术）

### 3.1 直觉：权重矩阵是"冗余"的

一个 768×768 的全连接层有 59 万参数。但研究表明：**它的有效秩（真正的信息维度）往往远小于 768**——大量方向是冗余的。

**低秩分解**就是把大矩阵 $W$ 拆成两个小矩阵的乘积：

$$W_{768 \times 768} \approx A_{768 \times r} \times B_{r \times 768}$$

其中 $r \ll 768$（如 r=64）。

参数从 768×768 = 59 万 → 768×64 + 64×768 = 9.8 万（**减少 84%**）。

### 3.2 怎么做（SVD 分解）

```python
import torch

# 假设有一个权重矩阵 W（768 x 768）
W = model.classifier.weight.data

# 奇异值分解
U, S, Vh = torch.linalg.svd(W, full_matrices=False)

# 只保留前 r 个奇异值
r = 64
U_r = U[:, :r]            # 768 x 64
S_r = torch.diag(S[:r])   # 64 x 64
Vh_r = Vh[:r, :]          # 64 x 768

# 用两个小矩阵近似原矩阵
W_low_rank = U_r @ S_r @ Vh_r     # 768 x 768（近似还原）
```

实际部署时**不还原**，而是把一层拆成两层：

```python
# 原来：Linear(768, 768)  → 参数量 768×768
# 拆成：Linear(768, 64) → Linear(64, 768) → 参数量 768×64 + 64×768

model.classifier = nn.Sequential(
    nn.Linear(768, 64, bias=False),
    nn.Linear(64, 768, bias=False),
)
```

> 🔥 **关键理解**：前向计算量也下降了——原来是 $O(768 \times 768)$ 的矩阵乘法，现在是 $O(768 \times 64) + O(64 \times 768)$。

### 3.3 低秩分解的三个坑

| 坑 | 说明 | 解决 |
|---|---|---|
| **r 选太小** | 精度骤降 | 按评估结果调（64/128/256 试） |
| **只分解不微调** | SVD 是近似，误差累积 | 分解后要**轻微微调**恢复精度 |
| **位置选错** | 有些层分解收益低 | 优先分解大矩阵（FFN 层、大分类头） |

## 四、初识：其他三种技术要点

### 4.1 量化（最常用）

```python
# PyTorch 动态量化（一行代码，无需重训）
quantized_model = torch.quantization.quantize_dynamic(
    model, {torch.nn.Linear}, dtype=torch.qint8
)
```

| 类型 | 说明 |
|---|---|
| **训练后量化（PTQ）** | 直接量化，简单但有精度损失 |
| **量化感知训练（QAT）** | 训练时模拟量化，精度更好但要重训 |
| INT8 | 最常用（4× 压缩、几乎无损） |
| INT4 | 更激进（大模型常用 GPTQ/AWQ） |

### 4.2 剪枝

```text
训练 → 按权重绝对值排序 → 剪掉最小的 30% → 微调恢复 → 再剪 → 循环
```

结构化剪枝（删整个神经元/通道）才能真正加速；非结构化剪枝（删单个权重）只省存储不省计算。

### 4.3 知识蒸馏

```text
大模型（Teacher）→ 输出软标签（各类别概率分布）
小模型（Student）→ 学习软标签（比硬标签信息更多）
```

> 💡 软标签的妙处：它包含"这个样本像 70% 军事、25% 历史"这种**类间相似信息**，比 one-hot 教得多。
>
> 大模型场景的延伸：**用 LLM 标注数据，蒸馏到小模型**——这是当下最实用的路线之一。

## 五、初识：压缩后的评估（别只看体积）

| 指标 | 说明 |
|---|---|
| 效果损失 | macro-F1 下降多少（< 2% 可接受） |
| 推理延迟 | P50/P99 实测（不是理论值） |
| 内存/显存 | 峰值占用 |
| 吞吐 | QPS（配合批处理） |

> ⚠️ 常见翻车：**压缩了 4 倍，延迟只降了 1.2 倍**——因为瓶颈在别处（如 CPU 算子不支持）。**必须实测**。

## 六、总结

### 6.1 要点回顾

1. 压缩的动机：**延迟、成本、部署环境**
2. 四种技术：**量化（最省事）、剪枝（删冗余）、蒸馏（大教小）、低秩分解（拆矩阵）**
3. 低秩分解：$W ≈ A×B$，用 SVD 找有效秩，把 1 层拆成 2 层，**参数量和计算量双降**
4. 低秩三坑：r 太小、不微调、层选错
5. 工程上**组合使用**；压缩后必须**实测延迟**，别只看体积

### 6.2 自测清单

<details>
<summary>Q1：四种压缩技术的核心区别？</summary>

量化降数值精度（FP32→INT8），剪枝删不重要的连接，蒸馏让小模型学大模型的输出分布，低秩分解把大矩阵拆成两个小矩阵。
</details>

<details>
<summary>Q2：低秩分解为什么能减少计算量？</summary>

把一次 768×768 的乘法拆成 768×64 与 64×768 两次乘法，参数量与 FLOPs 都大幅下降。
</details>

<details>
<summary>Q3：量化为什么常用 INT8？</summary>

INT8 相对 FP32 压缩 4 倍，主流硬件（CPU/GPU）对 INT8 有专门加速指令，精度损失通常很小。
</details>

<details>
<summary>Q4：压缩后效果掉了怎么办？</summary>

分解/剪枝后做少量微调恢复；或提高 r、降低剪枝比例；也可用蒸馏补偿。
</details>
