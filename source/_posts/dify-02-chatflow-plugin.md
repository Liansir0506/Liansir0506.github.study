> **一句话概括**：Dify 把"多步 AI 逻辑"做成 DAG 流程图——对话场景用 Chatflow（带记忆），批处理场景用 Workflow（纯流程）。
> **这篇有多重要**：📌 —— 平台使用能力；面试问"工作流怎么设计""对话流和 workflow 区别"能答。
> **前置知识**：dify-00 的五种应用类型、coze-01 的工作流概念
> **对应素材**：`03-dify/01-讲义/① 1.2Dify的入门实战`、`③ 3.1 智能法律助手`（对话流部分）

## 一、初识：五种应用类型怎么选

| 类型 | 输入→输出 | 有对话记忆 | 适合 |
|---|---|---|---|
| **聊天助手** | 对话 | ✅ | 客服、问答、闲聊 |
| **文本生成** | 单次文本 | ❌ | 写作、翻译、总结 |
| **Agent** | 对话 | ✅ | 需要调工具、自主规划 |
| **工作流 Workflow** | 单次任务 | ❌ | 批量处理、内容流水线 |
| **对话流 Chatflow** | 对话 | ✅ | **多轮交互 + 分支逻辑**（业务系统主力） |

选择口诀：

> **要对话就 Chatbot/Chatflow，要批处理就 Workflow，要自主决策就 Agent。**

### 1.1 Chatflow vs Workflow（面试常问）

| 维度 | Workflow | Chatflow |
|---|---|---|
| 是否多轮 | ❌ 一问一答就结束 | ✅ 支持多轮对话 |
| 记忆 | 无 | 有（可开启 memory） |
| 输入 | 表单/API 传入变量 | 用户对话 + 变量 |
| 典型场景 | 批量生成、数据清洗 | 客服、咨询助手、业务办理 |
| 类比 | 函数（无状态） | 带会话状态的函数 |

> 📌 记住这个类比：**Workflow = 无状态函数，Chatflow = 有状态的服务（会记住聊到哪了）**。

## 二、初识：常用节点

Dify 的编排画布和 Coze 很像，核心节点：

| 节点 | 作用 | 备注 |
|---|---|---|
| **开始** | 定义输入变量 | 用户问题、上传文件等 |
| **意图识别** | 判断用户想干什么，分流 | 一个节点搞定分类+路由（LLM 分类器） |
| **LLM** | 调用大模型（写 Prompt） | 用 `{{变量}}` 引用上游数据 |
| **知识检索** | 查知识库 | 可设 top-k、rerank、阈值 |
| **条件分支** | if/else | 按变量值分流 |
| **代码** | 写一小段 Python/JS | 数据格式处理 |
| **HTTP 请求** | 调外部 API | 接自己的业务系统 |
| **模板转换** | 拼接字符串/JSON | 组装最终输出 |
| **结束** | 定义输出 | 返回给用户 |

### 2.1 变量引用（Dify 的核心语法）

节点之间靠变量传递，写法是 `{{#节点ID.变量名#}}`：

```text
# 引用用户输入
{{#sys.query#}}

# 引用知识检索节点的结果
{{#context#}}

# 引用某个节点的输出字段
{{#1763643919240.text#}}
```

> 💡 和 Coze 的变量引用逻辑一样：**上一步的输出就是下一步的输入**，靠 ID 串起来。

## 三、初识：插件——接外部世界

Dify 的插件市场里有官方和第三方插件：搜索、网页抓取、数据库查询、各类 API 封装。

**典型用法：数据库查询插件**

法律助手项目里有个"资费查询"需求——律师费存在律所的本地数据库里。

```text
用户："你们的律师费怎么收？"
  ↓ 意图识别 → 资费查询
  ↓ 数据库查询插件（配置好 SQL/连接）
       SELECT price_range FROM lawyer_fee WHERE case_type = ?
  ↓ 把查询结果交给 LLM 组织语言
  ↓ 输出
```

> 🔥 这就是 Dify 相比 Coze SaaS 版的关键优势：**能连自己内网的数据库**（因为 Dify 部署在你自己的环境里）。

## 四、运用：一个对话流长什么样

以"客服助手"为例，一张典型的 Chatflow：

```text
开始（用户输入）
  ↓
意图识别节点
  ├─ 产品咨询 → 知识检索（产品手册）→ LLM 总结 → 输出
  ├─ 售后问题 → 收集订单号（多轮追问）→ HTTP 请求查订单 → 输出
  ├─ 转人工   → 输出"正在为您转接…"
  └─ 其他     → LLM 闲聊兜底
```

**设计要点**：

| 要点 | 说明 |
|---|---|
| 意图识别放在最前面 | 一次分流，后面每条路各管各的 |
| 每条分支独立闭环 | 一条路出错不影响其他路 |
| 兜底分支必须有 | 意图识别失败也要有"其他" |
| 关键节点可加记忆 | 让 LLM 知道前文（查询改写、追问都用得上） |

## 五、总结

### 5.1 要点回顾

1. 五种应用：聊天助手 / 文本生成 / Agent / **Workflow** / **Chatflow**
2. **Chatflow 有对话记忆，Workflow 没有**——Workflow 像无状态函数，Chatflow 像有状态服务
3. 常用节点：意图识别、LLM、知识检索、条件分支、代码、HTTP、模板转换、结束
4. 变量引用 `{{#节点ID.字段#}}` 把节点串成流水线
5. 插件让 Dify 能接外部世界——**数据库查询插件是私有化部署的杀手级能力**

### 5.2 自测清单

<details>
<summary>Q1：Chatflow 和 Workflow 的核心区别？</summary>

Chatflow 支持多轮对话、有记忆，适合咨询/客服类交互；Workflow 是一次性任务流、无状态，适合批量处理和内容生成。
</details>

<details>
<summary>Q2：意图识别节点一般放在哪？为什么？</summary>

放在流程最前面，先分流再进入各业务分支——这样每条分支的 Prompt 和工具都能精简，改动互不影响。
</details>

<details>
<summary>Q3：Dify 的插件能干什么？举例。</summary>

封装外部能力：搜索、网页抓取、数据库查询、第三方 API。数据库查询插件可让 AI 直接查业务库（私有化部署时）。
</details>

### 5.3 面试视角（📌）

| 面试问法 | 答题要点 |
|---|---|
| Dify 应用类型怎么选？ | 对话→Chatflow/Chatbot；批处理→Workflow；自主决策→Agent |
| 对话流怎么设计？ | 开始→意图识别分流→各分支独立闭环→兜底分支→统一输出 |
| 节点间数据怎么传？ | 变量引用（节点 ID + 字段名） |
| 平台编排和代码编排的取舍？ | 平台快速可视化、但复杂逻辑/高并发仍要代码（LangGraph） |
