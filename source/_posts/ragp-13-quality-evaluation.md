> **一句话概括**：RAG 调优不能靠"感觉好像好点了"——建评测集、量化指标、归因 Bad Case，才有真正的改进闭环。
> **这篇有多重要**：🔥 —— 面试问"你怎么评估 RAG 效果""怎么定位效果差的原因"，这是最能体现工程能力的一题。
> **前置知识**：ml-03 的评估指标、ragp-08 的检索调优
> **对应素材**：`RAG2/01_课件/site/14-rag-quality.html`、`17-quality-evaluation.html`

## 一、初识：RAG 评测要分两层

RAG 有两段可能出错：**检索**（找没找对）和**生成**（说的对不对）。必须分开评估：

| 层 | 指标 | 回答什么问题 |
|---|---|---|
| **检索层** | Recall@K、Hit Rate、MRR | 该找到的找到了吗？ |
| **生成层** | 忠实度（Faithfulness）、相关性、引用准确率 | 回答有没有依据、切不切题？ |

> 🔥 关键认知：**检索错了一切皆错**。如果正确片段没召回，生成层再优化也没用——所以先看检索，再看生成。

## 二、运用：评测集怎么建

### 2.1 最小评测集的三个字段

| 字段 | 内容 |
|---|---|
| `question` | 用户真实问法（含口语化） |
| `ground_truth` | 标准答案（人工撰写） |
| `expected_chunk_ids` | 应命中的 chunk（用于算召回） |

```jsonl
{"question": "退款要多久到账？", "ground_truth": "审核通过后 3 个工作日内到账", "expected_chunk_ids": ["kb1_doc3_2"]}
{"question": "XR-2000 怎么恢复出厂设置？", "ground_truth": "长按电源键 10 秒，指示灯闪红即可", "expected_chunk_ids": ["kb1_doc8_1"]}
```

### 2.2 评测集建设原则

| 原则 | 说明 |
|---|---|
| **覆盖类型** | FAQ / 文档 / 型号类 / 多跳 / 拒答（该拒的必须拒） |
| **来源真实** | 从真实日志/工单里捞，不要自己编 |
| **规模够用** | 首版 50~100 条就能发现大问题 |
| **持续扩充** | 每个 Bad Case 都沉淀进评测集 |

> 📌 特别建一类"**应该拒答**"的问题（如"公司股票代码是多少"）——测系统会不会瞎编。

## 三、初识：生成层的两个核心指标

### 3.1 忠实度（Faithfulness）

回答的每个结论是否都能在检索到的资料里找到依据。

```text
回答："退款需要 7 天内在 APP 提交 [1]，审核后 3 个工作日到账 [2]"
                                                        ↑
                              能否在资料 [1][2] 里找到对应内容？
```

衡量方式：

- **引用校验**（自动）：回答里每个 [n] 是否存在于资料编号
- **LLM 评审**（半自动）：让另一个模型判断"结论是否有资料支撑"
- **人工抽样**（黄金标准）：每周抽 20 条核对

### 3.2 相关性（Answer Relevance）

回答是否切题（不是答非所问，即使内容有依据）。

### 3.3 RAGAS 这类工具

| 工具能力 | 说明 |
|---|---|
| faithfulness | 忠实度 |
| answer_relevancy | 回答相关性 |
| context_precision / recall | 检索上下文质量 |

> ⚠️ 局限：这些指标本身也依赖 LLM 打分——**有噪声，适合看趋势和相对变化**，不能当绝对真理。人工抽样仍是必要的。

## 四、运用：Bad Case 闭环（真正产生价值的部分）

### 4.1 四步闭环

```text
① 收集：线上日志 + 用户反馈（点踩）→ 沉淀到 Bad Case 库
   ↓
② 归因：这次失败是"检索问题"还是"生成问题"？
   ↓
③ 修复：按归因采取对应动作
   ↓
④ 回归：把该 case 加入评测集，防止再犯
```

### 4.2 归因方法（关键）

| 观察 | 归因 | 修复方向 |
|---|---|---|
| 正确片段**没被召回** | 检索问题 | 切片/embedding/查询改写/混合检索参数 |
| 正确片段被召回但**排名靠后** | 排序问题 | Reranker、RRF 参数 |
| 召回正确、但回答**编造** | 生成问题 | Prompt 约束、温度、引用校验 |
| 召回正确、回答**答非所问** | 生成/上下文问题 | Prompt 结构、上下文顺序 |
| 资料本身就是**错的/过期的** | 知识问题 | 知识库治理（ragp-12） |
| 该拒答却**硬答** | 策略问题 | 阈值 + 拒答 Prompt |

> 🔥 **归因比修复更重要**：归错因，改动就是瞎调。方法：把"该命中的 chunk"和"实际召回的 chunk"打出来对比，一眼就能看出是检索还是生成的问题。

### 4.3 一个真实的归因案例

```text
用户问："XR-2000 和 XR-3000 的保修期一样吗？"

现象：回答"都是两年"——错误，XR-3000 是三年。

排查：
1. 看检索：只召回了 XR-2000 的保修条款（XR-3000 的没召回）
2. 归因：检索问题 → 型号词被向量检索泛化掉了
3. 修复：提高 BM25 权重 / 对型号做精确匹配预处理
4. 回归：把该问题加入评测集
```

## 五、初识：评测的三个层次（按投入排序）

| 层次 | 做法 | 频率 | 适合 |
|---|---|---|---|
| **L1 冒烟** | 10 个关键问题，人工看 | 每次改动 | 开发阶段 |
| **L2 评测集** | 50~100 条，算 Recall@K + 忠实度 | 每次上线前 | 迭代阶段 |
| **L3 线上监控** | 真实流量统计拒答率、点踩率、检索耗时 | 持续 | 生产阶段 |

> 📌 别一上来就搭复杂评测平台——**先有 50 条评测集，比有成套工具但没人跑更有价值**。

## 六、总结

### 6.1 要点回顾

1. RAG 评测分两层：**检索层（Recall@K）+ 生成层（忠实度、相关性）**
2. 评测集三字段：question / ground_truth / **expected_chunk_ids**；要有"应该拒答"的样本
3. 忠实度靠**引用校验 + LLM 评审 + 人工抽样**；RAGAS 看趋势不看绝对值
4. **Bad Case 闭环**：收集 → **归因（检索 vs 生成）** → 修复 → 回归进评测集
5. 归因是核心：把"应命中的"和"实际召回的"对比，就能定位问题在哪一层

### 6.2 自测清单

<details>
<summary>Q1：为什么评测要分检索层和生成层？</summary>

两段都可能出错，混在一起无法定位；分开量化才能知道是"没找到"还是"找到了但说错"。
</details>

<details>
<summary>Q2：忠实度怎么衡量？</summary>

引用校验（回答中的 [n] 是否存在且对应内容）+ LLM 评审（结论是否有资料支撑）+ 人工抽样核对。
</details>

<details>
<summary>Q3：Bad Case 怎么归因？</summary>

对比"应命中的 chunk"与"实际召回的 chunk"：没召回→检索问题；召回了但回答错→生成问题；资料本身错→知识治理问题。
</details>

<details>
<summary>Q4：为什么每个 Bad Case 都要进评测集？</summary>

防止回归：修复后要能自动验证；评测集越用越准，是长期质量保障的核心资产。
</details>

### 6.3 面试视角（🔥）

| 面试问法 | 答题要点 |
|---|---|
| 怎么评估 RAG 效果？ | 检索层 Recall@K/MRR + 生成层忠实度/相关性；评测集 + 人工抽样 + 线上指标 |
| 效果差怎么定位？ | Bad Case 归因：应命中 vs 实际召回对比，判断检索还是生成问题 |
| 评测集怎么建？ | 真实问题 + 标准答案 + 应命中 chunk；覆盖类型与拒答案例；持续沉淀 |
| RAGAS 可靠吗？ | 有参考价值但依赖 LLM 打分，看趋势；关键决策仍需人工抽样 |
| 上线后怎么监控质量？ | 拒答率、点踩率、引用校验失败率、检索耗时与命中率的趋势 |
