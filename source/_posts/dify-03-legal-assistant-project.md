## 一、初识：项目背景

老甲方"明德律师事务所"想在官网首页加一个**法律问答机器人**，期望四个功能：

| 功能 | 需求 |
|---|---|
| **法律条文查询** | 民诉、企业法顾、知识产权方向的法条原文查询 |
| **案情分析** | 用户描述案情 → 结合法条分析 |
| **合同审核** | 上传合同文件 → 找出风险点 |
| **资费查询** | 查律所律师费价格区间 |

价值：增加官网粘性 → 间接提高转化率。

> 💡 注意这个项目的两个**硬约束**（后面选型就靠它们）：
> 1. 资费数据在律所**本地数据库**
> 2. 机器人要**嵌入律所官网主页**

## 二、初识：技术选型的三个候选，为什么选 Dify

| 方案 | 判断 | 原因 |
|---|---|---|
| **Coze SaaS 版** | ❌ 排除 | ① 无法访问本地业务数据库；② 不支持把机器人嵌入自己主页 |
| **LangGraph** | ❌ 不划算 | 项目复杂度低、预算有限，用重框架性价比太低 |
| **Dify** | ✅ 采用 | 可私有化部署（能连本地库）、支持嵌入网页、开发成本低 |

> 🔥 这段是**面试可以直接讲的选型逻辑**：
> "先看硬约束（数据在哪、部署在哪），再权衡开发成本。硬约束一票否决——Coze SaaS 连不上本地库，直接出局；剩下两个按性价比选。"
>
> 呼应 coze-05：**不是平台好坏的问题，是场景匹配的问题。**

## 三、初识：整体架构

业务复杂度不算高，所以**一个对话流（Chatflow）**就装下了：

```text
开始（用户输入：文字 / 上传文件）
  ↓
意图识别节点（判断用户要干什么）
  ├─ 法律咨询 → 法条检索链路
  ├─ 案情分析 → 检索 + 分析链路
  ├─ 合同审核 → 文件读取 + 分类审核链路
  └─ 资费查询 → 数据库查询插件
```

知识库不是建在 Dify 里的，而是建在 **RAGFlow**（专业的 RAG 系统）里，Dify 通过"外部知识库"接入——这样检索能力更强、可独立维护。

## 四、运用：法律咨询链路（RAG 的完整示范）

这是整个项目最值得学的部分，四步：

```text
用户提问："公司不续签劳动合同要赔钱吗？"
  ↓ ① 查询改写
     "劳动合同到期不续签 经济补偿"
  ↓ ② 知识库检索（开启 rerank）
     召回法条原文
  ↓ ③ 结果优化（LLM + 检索结果）
     先给结论，再给法条依据
  ↓ ④ 输出 + 免责声明
```

### 4.1 第一步：查询改写（Query Rewrite）

**为什么改？** 用户说的是大白话（"要赔钱吗"），知识库里是法律术语（"经济补偿金"）——直接检索会漏。

Prompt 设计：

```text
系统：你是一个法律条文查询助手，请把用户的提问改写成更适合检索法条的表述。
用户输入：{{#sys.query#}}
```

> 🔥 **开启"记忆"**：让改写节点看到对话上文。比如用户先问"劳动合同"，接着问"那到期不续呢？"——有记忆才能补全成"劳动合同到期不续签"。
>
> 查询改写是 RAG 提效的**第一杠杆**：不改写，检索召回率直接打折。

### 4.2 第二步：检索 + rerank

- 召回 10 条左右
- **开启 rerank**：因为要返回给用户的是"法条原文"，不能塞一堆相关内容，必须把最准确的排前面

> 📌 这是 rerank 的典型用法：**输出精度要求高（法条原文不能错）时开 rerank**。

### 4.3 第三步：结果优化

```text
系统：你是法律咨询助手。根据用户问题和检索到的法条回答，
      先直接给结论，再给出对应的法律原文依据。
用户问题：{{#sys.query#}}
知识库结果：{{#context#}}
```

**"先结论后依据"** 这个输出结构是法律场景的刚需——用户要的是"能不能赔、赔多少"，法条是佐证。

### 4.4 第四步：输出 + 免责声明

```text
{{#节点输出#}}

以上分析内容来自律所智能大脑。如需进一步帮助，建议联系律所获取专业咨询，
电话：400-xxx-xxxx
```

> ⚠️ 法律/医疗/金融这类高风险场景，**免责声明是产品要求，不是可选项**。

## 五、运用：合同审核链路（更复杂的 RAG）

合同审核比法条查询复杂：要读文件、要按合同类型分流、要分风险点审核。

```text
上传合同文件
  ↓ ① 文件读取（解析合同文本）
  ↓ ② 拆解查询条件（LLM 判断这份合同涉及哪些法律条文）
  ↓ ③ 法条检索（召回 10 条）
  ↓ ④ 合同分类（劳动合同 / 技术服务合同 / 其他）
  ↓ ⑤ 分类型审核（每种合同一套独立 Prompt）
```

### 5.1 为什么要"合同分类"再审核

不同合同的审查重点完全不同：

| 合同类型 | 审核重点 |
|---|---|
| 劳动合同 | 试用期合法性、社保条款、竞业限制、解除条件 |
| 技术服务合同 | 交付标准、知识产权归属、验收条款、违约责任 |
| 其他 | 通用条款检查 |

> 💡 这就是 coze-05 讲的"意图分流"在审核场景的变体：**一份通用 Prompt 审所有合同 = 什么都审不细**，按类型拆分才能写出专业的审查规则。

### 5.2 审核 Prompt 的结构（值得参考）

```text
# 角色
你是一名资深劳动法律师，专注企业劳动合同合规审查。

# 审查背景
- 合同类型：劳动合同
- 我方立场：用人单位

# 审查要求
逐条检查以下风险点：试用期期限、社保缴纳、竞业限制补偿、解除条件…
输出格式：风险点 | 原文位置 | 风险等级 | 修改建议
```

> 这个"角色 + 背景 + 检查清单 + 输出格式"的四段式，是专业审核类 Prompt 的通用模板。

## 六、总结

### 6.1 要点回顾

1. 技术选型的顺序：**先看硬约束（数据/部署/嵌入），再看成本**——Coze SaaS 被硬约束排除，LangGraph 被成本排除
2. 架构：单个 Chatflow + 意图识别分发 + RAGFlow 外部知识库 + 数据库插件
3. **法律咨询四步**：查询改写 → 检索（rerank）→ 结果优化（先结论后依据）→ 输出 + 免责声明
4. **查询改写是 RAG 提效第一杠杆**，要开记忆补全上下文
5. **合同审核**：先分类再审核——一份通用 Prompt 审不了所有合同
6. 高风险场景（法律/医疗/金融）必须有免责声明

### 6.2 自测清单

<details>
<summary>Q1：这个项目为什么不用 Coze？</summary>

两个硬约束：资费数据在本地数据库（Coze SaaS 访问不了）、机器人要嵌入律所官网（SaaS 版不支持）；而 Dify 可私有化部署。
</details>

<details>
<summary>Q2：查询改写解决什么问题？</summary>

用户用口语提问，知识库是专业术语——直接检索会漏。改写把问题转成适合检索的表述，提升召回率；配合记忆可补全上下文。
</details>

<details>
<summary>Q3：法条查询为什么开 rerank？</summary>

用户要的是准确的法条原文，不能返回一堆相关但不精确的内容；rerank 能显著提升排序精度。
</details>

<details>
<summary>Q4：合同审核为什么要先分类？</summary>

不同合同类型的风险点完全不同，通用 Prompt 无法写出专业细致的审查规则；分类后每类用专属 Prompt 才审得细。
</details>

### 6.3 面试视角（📌 项目经验）

| 面试问法 | 答题要点 |
|---|---|
| 为什么选 Dify 不选 Coze？ | 硬约束优先：本地数据库 + 网页嵌入 → 必须私有化部署 |
| RAG 落地怎么做的？ | 查询改写 → 混合检索 + rerank → 结果优化（先结论后依据）→ 免责声明 |
| 合同审核怎么设计？ | 文件解析 → 法律要素拆解 → 检索 → 合同分类 → 分类审核 Prompt |
| 这类项目的风险点？ | 法条准确性（必须可溯源）、幻觉（要求引用原文）、合规（免责声明） |
