## 一、初识：单 Agent 的天花板

先看单 Agent 处理复杂业务的三个痛点：

| 痛点 | 具体表现 |
|---|---|
| **提示词臃肿** | 所有规则、流程、格式塞在一个 Prompt 里，几千字，模型抓不住重点 |
| **一处改动影响全局** | 改一个功能的规则，可能把另一个功能搞坏 |
| **调试困难** | 出错了不知道是哪段逻辑的问题 |

讲义里的原话很到位：**"调试时任何一处细节改动，都有可能影响到智能体的整体功能。"**

举个具体例子：做一个"小爱同学"式的语音助手，要控制空调、电视、电饭煲。如果全塞进一个 Agent：

- 提示词里要写清三种设备的操作规则
- 用户说"太热了"，模型得同时考虑"这是空调需求"和"具体怎么调"
- 加一个设备（比如扫地机器人），整个 Prompt 都得改

## 二、初识：主从模式（父子 Agent）

**拆开的思路**：

```text
用户 → 父 Agent（总指挥）
          ├─ 意图识别：你是在说空调？电视？还是电饭煲？
          └─ 任务分发：
               ├─ 空调 Agent：只管空调的所有操作
               ├─ 电视 Agent：只管电视的所有操作
               └─ 电饭煲 Agent：只管电饭煲的所有操作
```

| 角色 | 职责 | 特点 |
|---|---|---|
| **父 Agent（主）** | 接收任务、**意图识别**、**任务分解**、分发 | 全局视角，不干具体活 |
| **子 Agent（从）** | 处理某个领域的所有操作 | **职责单一、提示词精简** |

> 🔥 本质：**分治（divide and conquer）**。把一个大问题拆成互不干扰的小问题，每个小问题单独优化。

### 2.1 好处

1. **提示词短了**：每个子 Agent 只管一件事，Prompt 几百字就够
2. **改动隔离**：改空调规则不影响电视
3. **可并行**：多个子任务可以同时跑（部分平台支持）
4. **可复用**：子 Agent 是独立个体，能挂到别的父 Agent 下

### 2.2 代价

| 代价 | 说明 |
|---|---|
| 多一次路由调用 | 请求量更大、延迟略增 |
| 路由可能出错 | 父 Agent 判断错意图，就分发错了 |
| 上下文传递 | 子 Agent 需要知道"用户到底说了什么" |

## 三、运用：Coze 里的三种节点

创建 Multi-Agent 时，"添加节点"有三种类型：

| 节点类型 | 说明 | 适用 |
|---|---|---|
| **Agent 节点** | 轻量 Agent，只有提示词 + 技能 | 简单的对话型子任务 |
| **工作空间智能体** | 引用一个**已发布的完整 Agent**（带插件/工作流/知识库） | 复杂子任务（主流做法） |
| **全局跳转条件** | 只要用户输入满足条件，直接跳到某个 Agent | 强规则的分流（如"提到简历就进简历 Agent"） |

> 📌 实际项目里最常见：**父 Agent 做路由 + 多个"工作空间智能体"作为子 Agent**。因为真实业务的子模块往往已经很复杂（带插件、工作流、知识库），不可能用轻量 Agent 节点装下。

### 3.1 官方案例：多语言翻译

讲义里的入门案例，结构非常清晰：

```text
父 Agent：判断用户要翻译成什么语言，分发任务
  ├─ 中文 Agent：负责翻译成中文
  ├─ 日语 Agent：负责翻译成日文
  └─ 韩语 Agent：负责翻译成韩文
```

输入 `"Good morning" in Chinese` → 父 Agent 识别出"目标语言=中文" → 分发到中文 Agent → 返回"早上好"。

> 这个案例业务很简单（单 Agent 也能做），但用来理解"路由 + 分发"的结构刚刚好。

## 四、初识：什么时候该拆多 Agent

不是所有场景都要拆。判断标准：

| 该拆 | 不该拆 |
|---|---|
| 功能模块**天然独立**（不同设备/不同业务） | 只是同一个任务的不同步骤 |
| 单个 Agent 的提示词**超过 2000 字**还管不住 | 提示词精简单 Agent 能搞定 |
| 需要**不同子任务用不同模型**（贵的给难任务） | 所有任务难度差不多 |
| 多个团队**分别维护**不同模块 | 一个人维护 |

> ⚠️ 反模式：**为了"显得高级"而拆**。拆得不好，路由错误 + 上下文丢失，效果还不如单 Agent。

## 五、总结

### 5.1 要点回顾

1. 单 Agent 的三痛点：**提示词臃肿、改动影响全局、调试困难**
2. **主从模式**：父 Agent 做意图识别与分发，子 Agent 职责单一
3. Coze 三种节点：Agent 节点（轻量）、工作空间智能体（引用已发布 Agent，主流）、全局跳转条件（强规则分流）
4. 拆分的判断：**模块天然独立、提示词臃肿、需要异构模型、多团队维护**才拆
5. 拆分有代价：多一次路由、可能路由错、上下文要传递

### 5.2 自测清单

<details>
<summary>Q1：Multi-Agent 的主从模式怎么分工？</summary>

父 Agent：接收任务、意图识别、任务分解、分发；子 Agent：各管一个领域，职责单一、提示词精简。
</details>

<details>
<summary>Q2：Coze 的三种节点类型？</summary>

Agent 节点（轻量、只有提示词和技能）、工作空间智能体（引用已发布的完整 Agent，最常用）、全局跳转条件（按用户输入直接跳转）。
</details>

<details>
<summary>Q3：什么时候不该拆多 Agent？</summary>

任务只是同一流程的不同步骤、单 Agent 提示词能管住、模块不独立时——拆了反而增加路由错误和上下文丢失的风险。
</details>

### 5.3 面试视角（🔥）

| 面试问法 | 答题要点 |
|---|---|
| 什么是 Multi-Agent？ | 多个 Agent 分工协作，主 Agent 负责意图识别与分发，子 Agent 各自专精 |
| 多 Agent 的架构模式？ | 主从（Supervisor）、流水线（Pipeline）、网状（去中心化）；工程上主从最常用 |
| 怎么决定拆不拆？ | 模块独立性、提示词复杂度、模型异构需求、团队分工 |
| 多 Agent 的挑战？ | 路由准确率、上下文传递、成本与延迟、错误级联、状态管理 |
| 和 LangGraph 的关系？ | 同一思想的不同实现：Coze 可视化编排 vs LangGraph 代码化流程控制 |
