> **这篇有多重要**：🔥 —— 工作流是 Coze 最核心的能力，也是 Agent 编排的可视化形态；面试聊"怎么设计一个多步骤 AI 流程"直接用。

## 一、初识：三个东西的分工

先记住这句话：

> **插件是"零件"，工作流是"装配线"，Bot 是"产品"。**

| 概念 | 是什么 | 类比 |
|---|---|---|
| **插件（Plugin）** | 一个封装好的外部能力：搜索、查天气、生图、发 HTTP 请求 | 电动螺丝刀 |
| **工作流（Workflow）** | 把多个节点按顺序/条件编排起来 | 装配流水线 |
| **Bot（智能体）** | 最终对用户的产品：人设 + 技能 | 出厂的产品 |

### 1.1 插件 = Function Calling 的可视化版

回想 pe-03：Function Calling 的流程是"模型决定调什么工具 → 程序执行 → 结果回填"。

Coze 的插件完全一样：

- 你在界面上添加"搜索"插件
- 平台自动把插件的描述（JSON Schema）传给模型
- 模型觉得该搜，就输出调用请求
- 平台执行、把结果回填

**你不用写一行代码，但底层跑的是同一套机制。**

## 二、初识：工作流——可视化编排

### 2.1 工作流是什么

一个工作流 = 从"开始"到"结束"的一张流程图：

```text
开始（用户输入关键词）
  ↓
大模型节点（理解需求、提取搜索词）
  ↓
插件节点（调用搜索插件）
  ↓
代码节点（整理结果格式）
  ↓
大模型节点（总结成 3 条要点）
  ↓
结束（输出）
```

### 2.2 常用节点类型

| 节点 | 作用 | 对应概念 |
|---|---|---|
| **开始 / 结束** | 定义输入输出变量 | 函数签名 |
| **大模型节点** | 调用 LLM 处理（写 Prompt） | 一次模型调用 |
| **插件节点** | 调用插件 | Function Calling |
| **代码节点** | 写一小段 Python/JS 做数据加工 | 程序处理 |
| **条件分支** | if/else 分流 | 程序控制流 |
| **循环节点** | 对列表逐项处理 | for 循环 |
| **变量节点** | 存储/修改变量 | 局部变量 |

> 🔥 **看出来了吗**：这几乎就是一门"可视化编程语言"——条件、循环、变量、函数调用都有。所以工作流能干的活，写代码也能干；它的价值是**让不懂代码的人也能编排流程**。

### 2.3 一个实战：关键词 → 搜索 → 摘要

需求：用户输入一个话题，Bot 联网搜最新信息并总结 3 条要点。

```text
① 开始节点：入参 query（用户输入）
② 大模型节点「提炼搜索词」：
   Prompt：把用户的问题转成 1 个适合搜索引擎的关键词，只输出关键词。
③ 插件节点「搜索」：入参 = ②的输出
④ 代码节点「拼接」：把搜索结果拼成一段文本
⑤ 大模型节点「总结」：
   Prompt：根据以下搜索结果，总结 3 条要点，每条不超过 30 字：
   {{④的输出}}
⑥ 结束节点：输出 ⑤ 的结果
```

每一步都能单独调试（点开节点看输入输出）——这是工作流比"一个超长 Prompt"强的地方。

## 三、初识：什么时候该用工作流

| 场景 | 用 Prompt 就够 | 需要工作流 |
|---|---|---|
| 单轮问答 | ✅ | |
| 格式转换/改写 | ✅ | |
| 需要联网搜索 + 整理 | | ✅ |
| 多步骤 + 条件判断 | | ✅ |
| 需要精确控制每一步输出 | | ✅ |
| 批量处理 | | ✅（配合循环） |

**判断标准**：
- 一步能做完、结果要求不严 → Prompt
- 多步、有依赖、要精确控制 → 工作流

> 📌 经验：**工作流不是越多越好**。简单任务硬套工作流，只会增加维护成本和延迟。

## 四、运用：工作流的设计原则

### 4.1 每个节点只做一件事

❌ 一个节点里塞满"理解+搜索+总结+格式化"
✅ 拆成：理解 → 搜索 → 总结 → 格式化

理由：节点拆细了，出问题能定位在哪一步、能单独换模型、能复用。

### 4.2 数据结构要清晰

节点之间传的是变量。设计时先想清楚：

| 变量 | 类型 | 来源 |
|---|---|---|
| query | string | 开始节点 |
| search_keyword | string | 大模型节点 |
| search_results | array | 插件节点 |
| summary | string | 大模型节点 |

### 4.3 给失败留后路

- 插件调用失败 → 加条件分支，走"抱歉没搜到"的兜底
- 大模型输出格式不对 → 代码节点做校验/重试

> 真实项目和 demo 的区别就在这里：**demo 只跑成功路径，项目要考虑失败路径。**

## 五、总结

### 5.1 要点回顾

1. **插件 = 零件**（外部能力，就是 Function Calling 的可视化）、**工作流 = 装配线**、**Bot = 产品**
2. 工作流节点：开始/结束、大模型、插件、代码、条件分支、循环、变量
3. 工作流 = 可视化编程：能表达多步骤、条件、循环、数据加工
4. 用不用工作流看任务：一步能做完用 Prompt，多步/要精确控制才上工作流
5. 设计原则：**节点单一职责、数据结构清晰、失败路径要有兜底**

</details>

### 5.3 面试视角（🔥）

| 面试问法 | 答题要点 |
|---|---|
| 工作流是什么？和 Prompt 有什么区别？ | 可视化多节点编排；Prompt 是单次模型调用，工作流能表达多步/条件/循环/工具调用 |
| 工作流和代码编排的关系？ | 本质相同（DAG 编排）；工作流是低代码实现，代码框架（LangGraph）更灵活 |
| 怎么保证工作流稳定？ | 节点单一职责、输入输出校验、失败兜底分支、关键节点加日志 |
| Coze 工作流能做什么业务？ | 搜索问答、内容生成流水线、数据清洗、批量处理、审批/工单类多步任务 |
