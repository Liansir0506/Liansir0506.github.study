> **一句话概括**：RAG 的 Prompt 不是"写得好听"，而是"约束得死"——只依据资料、必须标引用、找不到就拒答。
> **这篇有多重要**：🔥 —— 生成质量的 80% 取决于 Prompt 约束；面试问"怎么减少幻觉"，答案就在这套模板里。
> **前置知识**：pe-01 的提示词基础、ragp-09 的 QAService
> **对应素材**：`RAG2/01_课件/site/10-rag-pipeline.html`

## 一、初识：RAG Prompt 与普通 Prompt 的区别

普通聊天 Prompt 追求"说得好"，RAG Prompt 的首要目标是"**说得对、有依据、不瞎编**"。

| 目标 | 手段 |
|---|---|
| 只用资料回答 | 明确约束 + 上下文格式 |
| 可追溯 | 要求标注引用编号 |
| 不硬答 | 拒答策略 |
| 输出稳定 | 结构化格式 + 低温度 |

## 二、运用：上下文注入的格式设计

### 2.1 带编号的上下文

```python
def build_context(chunks):
    lines = []
    for i, c in enumerate(chunks, start=1):
        lines.append(f"[{i}] (来源: {c.doc_id} 第{c.chunk_idx}段)\n{c.text}")
    return "\n\n".join(lines)
```

输出形如：

```text
[1] (来源: 退款政策.pdf 第3段)
退款申请需在购买后 7 天内提交，审核通过后 3 个工作日内到账。

[2] (来源: 售后手册.pdf 第12段)
若商品已拆封，退款需扣除 10% 包装费。
```

> 🔥 **为什么要编号**：模型可以在回答中用 `[1][2]` 标注依据——前端就能把引用高亮、点击跳原文。**这是 RAG 相对纯模型回答最大的价值**。

### 2.2 不要塞满

| 问题 | 后果 |
|---|---|
| 塞 10 段以上 | 上下文过长、模型注意力分散、成本高 |
| 混入不相关片段 | 误导生成、增加幻觉 |

> 经验：**精排后 3~5 段足够**，每段控制在 500 字内。

## 三、运用：RAG 的 Prompt 模板（可直接用）

```text
你是一个企业知识库问答助手。请严格按以下规则回答：

【规则】
1. 只依据【资料】中的内容回答，不得使用资料之外的知识
2. 每条结论后用 [编号] 标注来源，如：退款需在 7 天内申请 [1]
3. 如果资料中找不到答案，直接回答"根据现有资料无法回答这个问题"，不要编造
4. 如果资料互相矛盾，指出矛盾并分别标注来源
5. 回答简洁，先给结论，再给依据

【资料】
{context}

【问题】
{question}

【回答】
```

### 3.1 逐条解释为什么这样写

| 规则 | 作用 |
|---|---|
| "只依据资料" | 抑制模型用自身知识编造 |
| "标注 [编号]" | 可追溯、便于核对 |
| "找不到就说无法回答" | **拒答策略**，比瞎编好得多 |
| "资料矛盾要指出" | 真实文档常有冲突版本，硬合并会出错 |
| "先结论后依据" | 符合用户阅读习惯（dify-03 法律助手的做法） |

> 📌 特别注意**拒答话术要固定**：写死"根据现有资料无法回答这个问题"——这样后端可以用字符串匹配来统计拒答率（可观测性）。

## 四、运用：流式生成与中断

### 4.1 流式

```python
async def stream_answer(query, chunks):
    prompt = build_prompt(query, chunks)
    async for token in llm.astream(prompt):
        yield token
```

前端逐字显示——**首字延迟从 3 秒降到 0.5 秒**，体感完全不同。

### 4.2 中断与取消

用户关页面、发新消息时，要能取消正在跑的上游调用（省 GPU/费用）：

```python
try:
    async for token in stream:
        await asyncio.sleep(0)      # 让出控制权，允许取消
        yield token
except asyncio.CancelledError:
    # 客户端断开 → 清理资源
    await cleanup()
    raise
```

## 五、初识：生成后的三道后处理

| 检查 | 做法 | 失败处理 |
|---|---|---|
| **引用校验** | 检查回答里的 [n] 是否都存在于资料编号 | 移除无效引用 / 重新生成 |
| **敏感词** | 匹配黑名单 | 替换 / 拒答 / 转人工 |
| **格式校验** | 是否符合约定结构（如"结论+依据"） | 重新生成一次，再失败就返回原文片段 |

> 🔥 引用校验是**降低幻觉的最后一道闸**：模型编了一个 `[7]`，但资料只有 3 条——立刻能发现。

## 六、初识：Prompt 也要版本管理

Prompt 是"代码"，改一句可能影响所有回答：

| 做法 | 说明 |
|---|---|
| **Prompt 存配置文件/数据库** | 不写死在代码里，改了能热更新 |
| **带版本号** | `prompt_v3`，评估对比用 |
| **改前跑评测** | 用评测集对比新旧 Prompt 的忠实度/相关性（ragp-13） |
| **可回滚** | 新 Prompt 效果差，立刻切回旧版 |

> 📌 真实教训：某次为了"让回答更详细"改了一句 Prompt，结果拒答率暴涨（模型把"详细"理解成"必须编出细节"）——**没有评测集的修改就是赌博**。

## 七、总结

### 7.1 要点回顾

1. RAG Prompt 的核心是**约束**：只用资料、标引用、会拒答
2. 上下文：**带编号 + 来源元数据**，控制在 3~5 段
3. 五条规则：只依据资料、标注引用、找不到就说、矛盾要指出、先结论后依据
4. **拒答话术固定**，便于统计拒答率
5. 后处理三道闸：**引用校验、敏感词、格式校验**
6. Prompt 要版本化：配置化 + 改前跑评测 + 可回滚

### 7.2 自测清单

<details>
<summary>Q1：为什么上下文要编号？</summary>

让模型能引用 `[n]` 标注依据，实现可追溯；后端也能校验引用是否有效，发现编造。
</details>

<details>
<summary>Q2：怎么减少 RAG 的幻觉？</summary>

Prompt 约束（只依据资料/固定拒答话术）+ 低温度 + 引用校验 + 检索质量保证（找不到就不硬答）。
</details>

<details>
<summary>Q3：为什么拒答话术要固定？</summary>

便于后端用字符串匹配统计拒答率，作为质量与检索效果的监控指标；也让用户体验一致。
</details>

<details>
<summary>Q4：Prompt 为什么需要版本管理？</summary>

Prompt 直接影响所有回答，改动需可对比、可回滚；配置化能热更新，评测能防止"越改越差"。
</details>
