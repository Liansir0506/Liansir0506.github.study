> **一句话概括**：知识库不是"传一次就完事"——文档会变、会错、会被下架；治理就是让这些变化可控、可回滚。
> **这篇有多重要**：🔥 —— 企业级 RAG 与 demo 的最大差别之一；面试问"知识库怎么更新/怎么保证一致性"，答它。
> **前置知识**：ragp-03 的 Milvus、eng-04 的索引管线
> **对应素材**：`RAG2/01_课件/site/13-kb-versioning.html`、`13-knowledge-governance.html`、`15-ingestion-pipeline.html`

## 一、初识：知识不治理会出什么问题

| 场景 | 没治理的后果 |
|---|---|
| 政策更新了（退款从 7 天变 15 天） | 旧文档还在库里，答案新旧掺半 |
| 一份文档写错了 | 错误的答案被反复引用，没人发现 |
| 要紧急下架某份文档 | 不知道它在哪些 chunk 里，删不干净 |
| 新版本效果变差 | 没有版本对比，只能整体回滚或硬扛 |
| 半夜跑入库把服务搞挂了 | 没有隔离，影响线上 |

**知识库治理**要解决的就是这五件事：**入库管道、质量门禁、版本管理、灰度发布、回滚能力**。

## 二、初识：离线入库管道的五个阶段

```text
① 采集：上传/爬取/同步（带源信息：文档 ID、版本、更新时间）
   ↓
② 解析清洗：PDF/Word/HTML → 纯文本；去页眉页脚、去乱码
   ↓
③ 切片：按结构切（chunk_size 500 / overlap 50），保留元数据
   ↓
④ 向量化：统一 embedding 模型（批量、并发、失败重试）
   ↓
⑤ 写入：新版本写到"待激活"集合，不直接覆盖线上
```

### 2.1 解析是"隐形的地基"

| 格式 | 坑 |
|---|---|
| PDF 双栏 | 文字顺序错乱 |
| 表格 | 被拆成无意义的字符 |
| 扫描件 | 必须 OCR |
| 页眉页脚 | 每页重复，污染语义 |

> 📌 经验：**解析质量差，后面怎么做检索都是白搭**。上线前一定抽样看解析结果。

## 三、运用：版本管理（kb_version）

### 3.1 核心思想：入库与生效分离

```text
构建新版本 → 校验 → 写入 v2（不生效）→ 灰度 → 全量激活 → 旧版本保留可回滚
```

数据结构上，每条记录都带 `kb_version`：

```python
{"id": "kb1_v2_doc3_0", "vector": vec, "text": chunk,
 "kb_id": "kb1", "kb_version": "v2", "doc_id": "doc3"}
```

检索时带上版本条件：

```python
filter = f'tenant_id == "{t}" and kb_id == "{kb}" and kb_version == "{active_version}"'
```

> 🔥 好处：**切换版本 = 改一个 active_version 变量**（或配置），新版本不行就切回去，秒级回滚。

### 3.2 版本生命周期的五个状态

| 状态 | 说明 |
|---|---|
| `building` | 正在入库 |
| `validated` | 入库完成，通过质量门禁 |
| `gray` | 灰度（10% 流量） |
| `active` | 生效 |
| `archived` | 归档（保留 N 天可回滚） |

### 3.3 质量门禁（上线前的自动检查）

| 检查项 | 标准 |
|---|---|
| chunk 数量 | 与预期数量偏差 < 20%（防止解析失败导致大量丢内容） |
| 空 chunk 比例 | < 1% |
| 向量维度/数量一致性 | 与 schema 完全匹配 |
| 抽样检索自测 | 用固定 10 个问题测 Recall@5，达标才放行 |
| 敏感词扫描 | 命中则阻断发布 |

> 📌 **门禁是自动的**——人工不可能每次入库都检查几万条 chunk。

## 四、运用：增量更新怎么处理

全量重建的代价太大（几万文档 × embedding 费用）。增量更新是标配：

```python
def incremental_update(doc):
    # 1. 计算文档指纹（内容 hash）
    fp = hashlib.md5(doc.content.encode()).hexdigest()

    # 2. 未变化 → 跳过
    if get_doc_fingerprint(doc.id) == fp:
        return "skip"

    # 3. 删掉旧 chunk（按 doc_id）
    client.delete("chunks", filter=f'doc_id == "{doc.id}" and kb_version == "{active}"')

    # 4. 重新切片入库
    insert_chunks(doc, kb_version=active)
    update_doc_fingerprint(doc.id, fp)
```

三个坑：

| 坑 | 处理 |
|---|---|
| 删除后插入失败 | 先写新版本再切换（copy-on-write），别原地删 |
| 文档 ID 变更 | 用内容指纹兜底识别"同一文档" |
| 大量文档同时更新 | 排队 + 限速，避免 embedding API 被封 |

## 五、初识：治理的四个可观测点

| 指标 | 用途 |
|---|---|
| 入库成功率 / 失败原因分布 | 发现解析或网络问题 |
| 各版本 chunk 数 | 版本完整性 |
| 检索命中版本分布 | 确认灰度生效 |
| 文档更新延迟（从源更新到入库） | 知识时效性 |

## 六、总结

### 6.1 要点回顾

1. 知识是活的：会更新、会错、要下架——治理保证**可控、可回溯、可回滚**
2. 入库管道五阶段：**采集 → 解析清洗 → 切片 → 向量化 → 写入**
3. **version 与生效分离**：新版本写入不生效，切换 active_version 即秒级回滚
4. 版本五状态：building / validated / gray / active / archived
5. **质量门禁**自动化：数量、空块率、维度、抽样检索、敏感词
6. 增量更新用**内容指纹**判断变化，配合 copy-on-write 避免删了装不回来

### 6.2 自测清单

<details>
<summary>Q1：为什么入库要和生效分离？</summary>

入库可能失败或不完整；先构建到"待激活"状态，校验通过再切换，出问题可秒级回滚，不影响线上。
</details>

<details>
<summary>Q2：质量门禁一般检查什么？</summary>

chunk 数量偏差、空块比例、向量维度一致性、抽样检索 Recall、敏感词扫描——不合格阻断发布。
</details>

<details>
<summary>Q3：增量更新怎么判断文档变了？</summary>

计算内容指纹（如 MD5），与上次记录比对；变化才删旧 chunk 并重写，未变化跳过以省成本。
</details>

<details>
<summary>Q4：为什么检索要带 kb_version？</summary>

保证只检索当前生效版本，避免新旧版本混在一起导致答案不一致；也是灰度与回滚的实现基础。
</details>

### 6.3 面试视角（🔥）

| 面试问法 | 答题要点 |
|---|---|
| 知识库怎么更新？ | 离线管道解析切片入库；版本化 + 灰度 + 回滚；增量更新按内容指纹 |
| 怎么保证知识一致性？ | kb_version 隔离 + 检索带版本条件 + 门禁校验 |
| 更新出问题怎么回滚？ | 切换 active_version 指向旧版本，秒级生效 |
| 怎么防解析质量问题？ | 解析抽样检查 + 数量/空块率门禁 + 检索自测 |
| 大文档更新成本怎么控制？ | 增量更新（指纹比对）、批量并发、embedding 缓存 |
