> **一句话概括**：用自然语言描述意图、AI 生成代码、人负责拆解与验证——**这不是"躺平让 AI 写"，而是换一种方式当工程师**。
> **这篇有多重要**：🔥 —— VibeCoding 已经是行业默认工作方式。面试问"你怎么用 AI 写代码"，答得专业和答得业余差别很大。

## 一、初识：Vibe Coding 是什么

**定义**：用自然语言描述意图，由 AI 生成代码，**人负责拆解、验证与决策**。

一句最精辟的类比：

> **AI 是快的实习生，你是负责的工程师。**
>
> - 实习生写得快，但会犯错、会盲目自信、会"忘了"你之前说过的话
> - 工程师的活一点没少：**定任务、审代码、跑测试、担责任**

### 1.1 人机分工

| 你的职责 | AI 的职责 |
|---|---|
| 拆任务、写清需求 | 生成代码 |
| 读懂代码 | 解释代码 |
| 运行、测试、验证 | 修 bug |
| 决策与担责 | 写测试、写文档 |

### 1.2 AI 的四个"不能"（重点理解）

| 不能 | 表现 | 后果 |
|---|---|---|
| **不知道业务上下文** | 你不说，它只能猜 | 生成的代码不符合你的业务 |
| **不保证正确** | **幻觉**：编造不存在的 API、用过时的写法 | 代码跑不起来或暗藏 bug |
| **不做决策** | 架构选型、需求取舍它不负责 | 选错方案，返工 |
| **不担责任** | 上线事故，背锅的是你 | —— |

> 🔥 所以有一条铁律：**AI 的每一次输出都要验证**。"验证"这一步，就是你和"只会点按钮的人"的本质区别。

### 1.3 工具怎么选

| 工具 | 形态 | 特点 |
|---|---|---|
| **Cursor** | 独立 IDE | 一体化体验好 |
| VS Code + Copilot | 插件 | 适合已有 VS Code 习惯 |
| **Claude Code** | 终端命令行 | 适合大型项目、能读整个仓库 |
| 通义灵码 | VS Code 插件 | 免费、零门槛 |

> 建议：**只选一个用熟**。用熟比用多重要——工具会换，方法不会。

## 二、运用：五步循环（核心工作流）

```text
① 拆任务（写清楚要什么）
   ↓
② AI 生成代码
   ↓
③ 读懂 · 运行 · 验证        ← 绝对不能省的一步
   ↓ 通过？
   ├─ 否 → ④ 把报错/现象反馈给 AI → 回到 ②
   └─ 是 → ⑤ git commit → 下一个任务
```

### 2.1 每步要点

| 步骤 | 要点 |
|---|---|
| **① 拆任务** | 一次只让 AI 做一件**可验证的小事**（一个函数 / 一个接口） |
| **② 生成** | 给足需求、约束、验收标准、上下文（见下） |
| **③ 验证** | 读懂（每段在干嘛）→ 运行 → 测试 |
| **④ 反馈** | 贴**完整报错**，不是"它报错了" |
| **⑤ commit** | 通过就提交——每一步成功的中间状态都存下来 |

### 2.2 任务拆分标准（很实用）

> **每个子任务做完都能"运行验证"。**

| 坏 | 好 |
|---|---|
| "做一个问答系统" | "先做 GET /health 接口，返回 ok" |
| "写个爬虫" | "写一个抓取仓库列表的函数，返回 list，用固定 HTML 做测试" |

拆到"能跑起来看到结果"为止——这样每一步都有反馈，AI 也不会跑偏。

## 三、运用：提示词四要素

给 AI 提需求，和给同事派活一样——信息不全，结果必然不对：

| 要素 | 说明 | 例子 |
|---|---|---|
| **需求** | 要什么、**不要什么** | "写词频统计函数，输入文本返回 Counter，不要用第三方库" |
| **约束** | 技术栈、风格、环境 | "Python 3.11，注释中文，PEP 8" |
| **验收** | 怎么算完成 | "给出 3 个测试用例" |
| **上下文** | 相关文件、报错、规范 | "报错信息：……；相关代码：……" |

### 3.1 好 vs 坏提示词

| 坏 | 好 |
|---|---|
| "帮我写个接口" | "用 FastAPI 写 GET /users 接口，返回 JSON 列表，name 参数可选做模糊过滤，Pydantic 校验，附 2 个测试用例" |
| "它报错了" | "运行报错如下：```Traceback…```，环境 Python 3.11，预期是返回 200" |
| "优化一下" | "这个函数 1000 条数据耗时 2s，优化到 500ms 内，可以改数据结构" |

> 📌 记住：**"它报错了"是最没用的反馈**——AI 没有任何信息可用来定位。

## 四、运用：CLAUDE.md——让 AI 记住你的习惯

每次都要交代"用中文注释、PEP 8、先讲思路"？——写进配置文件，一劳永逸。

**CLAUDE.md 分两级**：

| 级别 | 位置 | 内容 |
|---|---|---|
| **个人级** | 用户配置目录 | 你的语言、技术栈、编码习惯（所有项目生效） |
| **项目级** | 仓库根目录 | 项目的技术栈、目录结构、团队规范（随仓库共享） |

个人模板：

```markdown
# 个人开发偏好

## 基本信息
- 回答语言：中文
- 角色：Python 开发者，解释代码时先讲思路再上代码

## 编码偏好
- Python 3.11，遵循 PEP 8
- 注释用中文，命名 snake_case
- 优先标准库，少引第三方依赖

## 沟通偏好
- 报错先给最可能的原因，再给修复方案
- 生成代码后附"如何验证"的说明
```

> ⚠️ **配置完必须验证**：新开一个对话让 AI 生成代码，检查是否真的符合偏好（注释语言？命名风格？）。**不验证的偏好等于没配置**——旧对话的上下文可能会覆盖它。

## 五、总结

### 5.1 要点回顾

1. VibeCoding = **自然语言描述意图 + AI 生成 + 人验证决策**
2. 核心认知：**AI 是快的实习生，你是负责的工程师**（验证、担责是你的活）
3. AI 四个不能：**不知上下文、不保证正确（幻觉）、不做决策、不担责任**
4. **五步循环**：拆任务 → 生成 → 验证 → 反馈 → commit（验证绝不能省）
5. 提示词四要素：**需求、约束、验收、上下文**；反馈要贴完整报错
6. CLAUDE.md 两级：个人级（习惯）+ 项目级（规范），**配完要验证**

### 5.2 自测清单

<details>
<summary>Q1："AI 是快的实习生"说明了什么？</summary>

AI 写得快但会犯错、盲目自信、忘记上下文——所以拆任务、给足上下文、验证输出、承担责任，一个都不能少。
</details>

<details>
<summary>Q2：五步循环中哪一步不能省？为什么？</summary>

第③步"读懂·运行·验证"。它是人与"只会点按钮的人"的区别；跳过验证，等于把未经检验的代码直接交给生产。
</details>

<details>
<summary>Q3：什么是幻觉？怎么应对？</summary>

AI 生成看似合理但错误的内容（编造不存在的 API、过时写法）。应对：验证每一次输出——读懂、运行、测试；可疑的库先查文档。
</details>

<details>
<summary>Q4：任务拆分到什么程度？</summary>

拆到每个子任务都能独立运行验证为止（如"先做 /health 接口返回 ok"）。
</details>

### 5.3 面试视角（🔥）

| 面试问法 | 答题要点 |
|---|---|
| 你怎么用 AI 辅助开发？ | 拆任务 → AI 生成 → 读懂验证 → 反馈迭代 → 提交；关键在验证与决策 |
| AI 生成的代码你敢直接用吗？ | 不直接用：读懂 + 单测 + Code Review；复杂逻辑自己重构 |
| 怎么让 AI 更懂你的项目？ | CLAUDE.md/规则文件（技术栈、规范、目录）、给足上下文、示例 |
| VibeCoding 的风险？ | 幻觉、安全漏洞、不可维护的"AI 屎山"——靠测试、审查、小步提交控制 |
| AI 会取代程序员吗？ | 取代"只写代码"的部分；需求拆解、架构决策、质量责任仍属于人 |
