> **一句话概括**：分支让多个人同时改代码互不干扰，PR 让改动被审查后再合并，回滚让你随时能退回安全状态。
> **这篇有多重要**：📌 —— 团队协作必备；面试问"你们团队怎么协作"，答"分支 + PR + Code Review"就对了。
> **前置知识**：eng-00 的三大区与日常命令
> **对应素材**：`vibecoding/01课件/docs/01-git.md`（1.3 远程仓库协作部分）

## 一、初识：为什么要有分支

假设你和同事同时改一个项目：

- 你在做"新增搜索功能"
- 同事在改"登录逻辑"

如果都在 `main` 分支上直接改——代码交错、谁也不知道哪行是谁的、上线时想只发你的功能都不行。

**分支（Branch）** 就是解法：**每个人在自己的分支上开发，完成后合并回主分支**。

```text
main     ──●──●──────────────●──   （稳定主线）
              \            /
feat-search    ●──●──●──●──        （你的功能分支）
```

> 默认主分支叫 `main`（老项目可能叫 `master`）。`main` 始终是"可上线"的状态。

## 二、运用：分支的四个动作

```bash
git branch                        # 查看分支
git checkout -b feat-search       # 新建并切换到 feat-search 分支
# 或新版写法：git switch -c feat-search

# 在分支上正常开发、commit…
git add .
git commit -m "feat: 添加搜索接口"

git checkout main                 # 切回主分支
git merge feat-search             # 把功能分支合并进来
```

### 2.1 命名规范

| 前缀 | 用途 | 例子 |
|---|---|---|
| `feat/` | 新功能 | `feat/user-search` |
| `fix/` | 修 bug | `fix/login-empty-password` |
| `docs/` | 文档 | `docs/deploy-guide` |

## 三、运用：Pull Request（PR）——合并前的"安检"

分支开发完后，**不要直接 merge 到 main**，而是开一个 **PR（Pull Request，合并请求）**：

```text
你的分支 → 发起 PR → 同事 Review → 通过后合并到 main
```

PR 做什么：

| 环节 | 价值 |
|---|---|
| **代码审查** | 同事看你的改动，发现 bug/设计问题 |
| **讨论记录** | 为什么这么改，留在 PR 里可追溯 |
| **CI 检查** | 自动跑测试、代码风格检查（第 9 章 CI/CD） |

> 🔥 **PR 是团队协作的核心机制**：不是"不信任你"，而是"多一双眼睛"。面试问"你们团队怎么保证代码质量"，第一个答案就是 Code Review。

## 四、运用：冲突——两个人改了同一行

### 4.1 冲突怎么产生

```text
main:    password = "123456"
你的分支: password = "******"      （你改了加密）
同事分支: password = "admin@123"   （他改了默认值）
```

两人合并时，Git 不知道听谁的——这就是**冲突（Conflict）**。

### 4.2 解决步骤

```bash
git pull        # 或 git merge main，Git 会提示冲突文件

# 打开冲突文件，会看到：
<<<<<<< HEAD
password = "******"
=======
password = "admin@123"
>>>>>>> main

# 手动改成最终想要的内容（可能需要和同事商量），删掉 <<<< ==== >>>> 标记

git add 冲突文件
git commit -m "fix: 解决密码字段的合并冲突"
```

> 📌 原则：**冲突不要瞎选一边**，先搞清楚两边为什么这么改，问清楚再合。选错了就是把别人的修复覆盖掉。

## 五、运用：写坏了怎么救（回滚三招）

| 场景 | 命令 | 说明 |
|---|---|---|
| **撤销工作区未提交的修改** | `git checkout -- file.py` | 丢弃本地改动，回到上次提交 |
| **撤销某次已提交的改动（安全）** | `git revert <commit-id>` | **生成一个反向提交**，历史保留，适合已推送的代码 |
| **回退到某个历史版本（重写历史）** | `git reset --hard <commit-id>` | ⚠️ 危险：丢弃之后的提交，已推送的会破坏他人历史 |

> 🔥 **revert vs reset 的区别（面试常问）**：
> - `revert`：**安全**，新增一个"撤销提交"，历史完整——团队协作环境用这个
> - `reset`：**危险**，直接把指针拨回去，之后的提交消失——只在自己的本地分支用

### 5.1 一个真实原则

> **已经 push 到共享分支的提交，永远用 revert，不要用 reset。**

因为别人可能已经基于你的提交在开发，reset 会让别人的历史错乱。

## 六、总结

### 6.1 要点回顾

1. **分支**：每个人在自己的分支开发，main 保持可上线
2. 分支命名规范：`feat/`、`fix/`、`docs/`
3. **PR（合并请求）**：代码审查 + 讨论记录 + CI 检查，是团队质量的第一道闸
4. 冲突：手动合两边意图，**别瞎选一边**
5. 回滚三招：`checkout --`（丢本地改动）/ **`revert`（安全撤销，推荐）** / `reset --hard`（危险，仅本地）

### 6.2 自测清单

<details>
<summary>Q1：为什么要用分支开发，而不是都在 main 上改？</summary>

隔离开发、互不干扰；main 保持稳定可上线；功能可以独立测试和合并；出问题影响范围小。
</details>

<details>
<summary>Q2：PR 的作用是什么？</summary>

代码审查（发现 bug/设计问题）、变更讨论留痕、自动 CI 检查，合并前的质量闸门。
</details>

<details>
<summary>Q3：revert 和 reset 的区别？该用哪个？</summary>

revert 生成反向提交、历史保留，安全，适合已推送的共享分支；reset 直接回退指针、丢弃后续提交，危险，只用于本地。团队协作优先用 revert。
</details>

### 6.3 面试视角（📌）

| 面试问法 | 答题要点 |
|---|---|
| 你们团队的协作流程？ | 分支开发 → PR + Code Review → CI 检查 → 合并 main → 部署 |
| 遇到代码冲突怎么办？ | 先理解双方改动意图、沟通后手动合并，合并后跑测试 |
| 线上出问题怎么回滚？ | `git revert` 生成反向提交或回退到上一个发布 tag；配合 CI/CD 快速重发 |
| 怎么避免冲突？ | 小步提交、频繁拉取 main、按模块划分分支、沟通好改动范围 |
