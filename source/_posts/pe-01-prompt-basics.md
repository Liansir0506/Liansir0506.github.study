> **一句话概括**：好提示词的三个核心动作——给模型一个身份（角色）、给几个例子（Few-shot）、让它一步步想（CoT）。
> **这篇有多重要**：🔥🔥 —— **面试必考**："Few-shot 和 CoT 是什么、为什么有效、什么时候用"。这两个概念现在几乎是所有大模型应用的默认配置。

> **对应素材**：`01-讲义/② 大模型提示词工程指南`、`02-代码/day01/04-few-shot的使用.py`、`05-chain-of-thought的使用.py`、`03-对话角色划分.py`

## 一、初识：一个合格 Prompt 的五个要素

别一上来就"帮我写个文案"。一个结构清晰的 Prompt 至少包含：

| 要素 | 作用 | 例子 |
|---|---|---|
| **角色** | 定义"你是谁" | "你是一名有 10 年经验的数据分析师" |
| **任务** | 要做什么 | "把这段销售数据总结成 3 条结论" |
| **上下文** | 背景信息 | "这是某电商平台 2026 年 Q3 的数据" |
| **输入** | 具体材料 | 数据表 / 文章 / 代码 |
| **输出格式** | 要什么样子 | "用 Markdown 表格输出，列名：结论 / 依据 / 建议" |

> 📌 经验法则：**你觉得"说清楚了"，模型往往还是没懂**。把要求写成"一个新人拿到就能干活"的程度，才叫清楚。

## 二、初识：角色设定——给模型一个"身份"

### 2.1 有没有角色的差别

```text
❌ 没有角色：
"解释一下什么是过拟合。"

✅ 有角色：
"你是一名带过很多新人的机器学习工程师。请用『给三个月经验的后端开发讲』的方式，
解释什么是过拟合，要求用生活化的类比，200 字以内。"
```

差别在哪：

- 没有角色 → 模型给你一段教科书定义
- 有角色 → 模型自动匹配**知识深度、语气、举例方式**

### 2.2 角色写法的三个原则

1. **具体**："资深后端工程师" 比 "程序员" 好
2. **带约束**："回答不超过 200 字 / 用表格 / 不要用行话"
3. **贴合任务**：写代码就给"工程师"，写文案就给"新媒体编辑"

## 三、初识：Few-shot——用例子教模型做事

### 3.1 Zero-shot vs Few-shot

| 方式 | 做法 | 适合 |
|---|---|---|
| **Zero-shot** | 只给指令，不给例子 | 简单任务（翻译、总结） |
| **Few-shot** | 给几个"输入 → 输出"示例，再让模型照做 | 格式复杂/风格特殊/判断标准模糊的任务 |

```python
messages = [
    {"role": "system", "content": "你是情感分类器，只输出：正面 / 负面 / 中性"},
    {"role": "user", "content": "这个手机续航太差了，一天要充两次。"},
    {"role": "assistant", "content": "负面"},
    {"role": "user", "content": "还行吧，跟描述基本一致。"},
    {"role": "assistant", "content": "中性"},
    {"role": "user", "content": "包装很用心，物流也快，五星好评！"},
]
# 模型的回复会模仿前两个例子的格式：「正面」
```

### 3.2 例子怎么挑（有讲究）

| 原则 | 说明 |
|---|---|
| **覆盖各种情况** | 分类任务要把每个类别都示范一次 |
| **格式严格一致** | 例子的输出格式 = 你想要的最终格式 |
| **典型，不要极端** | 用有代表性的例子，别用边缘案例 |
| **顺序有影响** | 模型对靠后的例子更敏感（近因效应），重要的放后面 |

> 🔥 **为什么 Few-shot 有效？** 模型在"上下文里找模式"（in-context learning）——它不需要更新参数，仅凭几个例子就能推断出任务规律。这也是大模型"会举一反三"的来源。

## 四、初识：思维链 CoT——让模型"先想再答"

### 4.1 问题：模型容易"张口就来"

直接问复杂问题，模型往往给出**看似合理但错误**的答案——因为它跳过了推理过程，直接套模式。

### 4.2 CoT 的做法

就是在 Prompt 里加一句：

```text
请一步一步思考，给出详细的推理过程，再给结论。
```

看代码里的经典例子：

```python
prompt = """
我家距离洗车店 200 米，我要去洗车，是应该开车去，还是走路去？
请你一步一步推导，到底该怎么完成洗车，给出思考的过程。
"""
```

模型会这样推理：

> 洗车的对象是"车"，人走路去就没车可洗；所以要先把车开到洗车店；200 米虽近，也必须开车去……

**没有 CoT**，模型很可能直接答"走路去，200 米很近"——掉进陷阱。

### 4.3 CoT 为什么有效（面试要答这个）

| 原因 | 说明 |
|---|---|
| **把隐式计算变成显式 token** | 每一步推理都生成成文字，后续步骤基于前面写下的中间结果，相当于"打草稿" |
| **降低单步难度** | 一次只做一小步，模型更容易做对 |
| **可追溯** | 推理过程写出来了，错了能定位在哪一步 |

> 📌 局限：CoT 对**数学/逻辑推理**提升明显；对简单事实问答反而可能啰嗦、甚至"想多了出错"。而且 CoT 会让输出变长（成本更高）。

### 4.4 CoT 的三种写法

| 写法 | 做法 | 例子 |
|---|---|---|
| **零样本 CoT** | 只加一句"让我们一步一步思考" | `请逐步推理` |
| **少样本 CoT** | 给带推理过程的例子 | 例子里包含"因为…所以…"的推导 |
| **结构化 CoT** | 指定推理框架 | "先分析条件，再列公式，最后计算" |

## 五、运用：三者组合起来

真实项目里，这三个技巧几乎总是一起用：

```python
messages = [
    {"role": "system", "content": """你是一名资深金融分析师。
分析股票公告时，严格按以下步骤：
1. 提取关键信息（公司、事件、金额）
2. 判断事件性质（利好/利空/中性）
3. 给出影响评估
输出格式：{"company": "", "event": "", "sentiment": "", "reason": ""}"""},

    # Few-shot：给一个完整的示范
    {"role": "user", "content": "某公司拟回购不超过 5 亿元股份用于员工持股计划"},
    {"role": "assistant", "content": """{"company":"某公司","event":"股份回购5亿元","sentiment":"利好","reason":"回购通常传递管理层对公司价值的信心，且用于员工持股有利于绑定核心团队"}"}"""},

    {"role": "user", "content": "【待分析的公告原文】"}
]
```

角色（金融分析师）+ 步骤（结构化 CoT）+ 例子（Few-shot 示范格式）——这就是一个生产级的 Prompt。

## 六、总结

### 6.1 要点回顾

1. Prompt 五要素：**角色、任务、上下文、输入、输出格式**
2. 角色设定不是玄学：它决定了模型匹配什么知识深度、语气和举例方式
3. **Few-shot**：给"输入→输出"示例，利用大模型的 in-context learning 能力；例子要覆盖全面、格式一致、典型
4. **CoT（思维链）**：让模型"一步步想"——把隐式计算变成显式 token，降低单步难度、可追溯
5. CoT 对推理题有奇效，对简单问答可能画蛇添足；输出变长 = 成本上升

### 6.2 自测清单

<details>
<summary>Q1：Few-shot 为什么有效？</summary>

大模型具备 in-context learning 能力：不需要更新参数，仅凭上下文里的几个示例就能推断任务模式和输出格式。
</details>

<details>
<summary>Q2：CoT 为什么能提升推理准确率？</summary>

把推理过程写出来（生成中间 token），相当于给模型"打草稿"：每步只处理一小段逻辑、结果显式保留，比一步到位更可靠。
</details>

<details>
<summary>Q3：什么时候不该用 CoT？</summary>

简单事实问答、格式转换、追求低延迟/低成本的场景——CoT 会增加 token 消耗，甚至引入多余推理导致出错。
</details>

<details>
<summary>Q4：Few-shot 的例子怎么挑？</summary>

覆盖所有类别和边界情况、输出格式与期望完全一致、例子典型不极端、重要示例放在靠近提问的位置。
</details>

### 6.3 面试视角（🔥 必背）

| 面试问法 | 答题要点 |
|---|---|
| Zero-shot / Few-shot / CoT 区别？ | 无示例 / 给示例 / 要求分步推理；Few-shot 靠 in-context learning，CoT 靠显式中间步骤 |
| Few-shot 为什么有效？ | 上下文学习：示例激活模型的模式匹配能力，约束输出格式与风格 |
| CoT 的原理和局限？ | 分解推理步骤、显式中间结果；局限是成本增加、简单任务反而变差 |
| 如何让输出格式稳定？ | Few-shot 示范格式 + 明确输出模板（JSON schema）+ 温度调低 |
| Prompt 写不好怎么办？ | 拆解五要素、补示例、强制分步、指定输出格式、迭代测试 |
