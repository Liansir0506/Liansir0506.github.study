> **一句话概括**：RAG 在工程上就两条管线——离线把文档"做成可检索的索引"，在线把问题"检索出相关片段再让模型回答"。
> **这篇有多重要**：🔥🔥 —— **RAG 是所有企业级 AI 应用的主流架构**。前面 dify-01 讲了检索原理，这篇讲工程落地；后面项目篇的 RAG 系统会在这条管线上加料。
> **前置知识**：dify-01 的三种检索、nlp-02 的 embedding
> **对应素材**：`vibecoding/01课件/docs/04-rag.md`（4.1 RAG 原理总览）

## 一、初识：为什么需要 RAG（三个理由）

| 问题 | 说明 |
|---|---|
| **知识截止** | 模型只知道训练数据里的东西，之后发生的事不知道 |
| **私有知识** | 公司文档、产品手册它没见过 |
| **幻觉** | 不知道也会编——而且编得很像真的 |

RAG（Retrieval-Augmented Generation）的思路：**回答前先查资料，拿着资料再回答**。

### 1.1 RAG vs 微调（面试必答）

| | RAG | 微调 |
|---|---|---|
| 本质 | 外挂知识（检索） | 改模型参数 |
| 适合 | **事实类知识**（文档/FAQ/法条） | **风格/格式/领域能力** |
| 更新 | 改文档即生效 | 需重新训练 |
| 成本 | 低 | 高 |
| 可溯源 | ✅ 能给出处 | ❌ 说不清 |

> 结论：**"知识查得到用 RAG，风格学得像用微调"**。绝大多数企业场景选 RAG。

## 二、初识：两条管线（RAG 的工程骨架）

RAG 系统在工程上分两条**完全独立**的管线：

```text
【离线】索引管线（Indexing）—— 入库时跑一次
文档 → 解析 → 切片 → 向量化 → 存入向量库

【在线】查询管线（Querying）—— 每次提问都跑
问题 → 改写 → 检索 → 重排 → 拼装 Prompt → 生成回答
```

> 🔥 **为什么分开？**——离线管线是"重活"（解析 PDF、算几万条向量），耗时但只需跑一次；在线管线必须"快"（几百毫秒内），所以只能用轻量操作。两条管线分开设计，才能既准又快。

## 三、运用：索引管线四步

### 3.1 第一步：解析（Parsing）

把各种格式变成纯文本：

| 格式 | 工具 |
|---|---|
| PDF | PyMuPDF、pdfplumber |
| Word | python-docx |
| HTML | BeautifulSoup |
| 扫描件 | OCR（PaddleOCR 等） |

**坑**：PDF 的表格、双栏排版、页眉页脚——解析出来经常是乱的。解析质量差，后面全白搭。

### 3.2 第二步：切片（Chunking）

把长文档切成小段（chunk）：

| 策略 | 做法 | 适合 |
|---|---|---|
| 固定长度 | 每 500 字切一刀，重叠 50 字 | 通用 |
| 按结构 | 按标题/段落/句子切 | 结构化文档（推荐） |
| 父子分块 | 子块检索、父块喂模型 | 精度和上下文都要（dify-01 讲过） |

**参数建议**：

```text
chunk_size：300~800 字
overlap：10%~20%
```

> ⚠️ 切片是 RAG 最影响效果的环节之一：切太大 → 检索不准；切太小 → 语义不完整。

### 3.3 第三步：向量化（Embedding）

每段文本 → 一个向量：

```python
from openai import OpenAI
client = OpenAI()

def embed(text: str) -> list[float]:
    res = client.embeddings.create(
        model="text-embedding-v3",     # 或 bge-m3、m3e 等
        input=text
    )
    return res.data[0].embedding       # 例如 1024 维
```

> 📌 **关键决策：embedding 模型要统一**——入库用什么模型，查询就必须用什么模型。换了模型，向量空间不兼容，必须全部重算。

### 3.4 第四步：入库

```python
# 伪代码：向量库（Milvus / Qdrant / pgvector / Chroma）
collection.insert([
    {"id": f"doc{i}_chunk{j}", "vector": vec, "text": chunk,
     "metadata": {"source": "产品手册.pdf", "page": 3}}
])
```

存的不只是向量——还要存**原文和元数据**（来源、页码），因为：
- 检索出来要把原文喂给模型
- 回答要能标注出处

## 四、运用：查询管线五步

### 4.1 改写（Query Rewrite）

用户问："这个怎么退？"——"这个"指什么？口语怎么转成检索友好的表达？

```text
用户：上次买的那个耳机，坏了能换吗？
改写：耳机 售后 退换货 政策
```

> dify-03 的法律助手里，查询改写就是提效第一杠杆。

### 4.2 检索（Retrieval）

问题向量化 → 在向量库里找最相似的 top-k：

```python
q_vec = embed(question)
hits = collection.search(q_vec, top_k=20)     # 粗排多取一些
```

> 生产环境通常是**混合检索**：向量检索 + 关键词检索（BM25），两路合并。

### 4.3 重排（Rerank）

把 top-20 交给 rerank 模型重新打分，取 top-3~5：

```python
reranked = rerank_model(question, [h["text"] for h in hits])
top_chunks = reranked[:4]
```

> 两阶段（粗排召回 → rerank 精排）是精度关键，dify-01 已经讲过原理。

### 4.4 拼装 Prompt（Augmentation）

```python
prompt = f"""
请只根据以下资料回答问题；资料里没有的信息，回答"根据现有资料无法回答"。

【资料】
{chr(10).join(top_chunks)}

【问题】
{question}
"""
```

两个关键约束：

- **"只根据资料回答"**——抑制幻觉
- **"没有就说没有"**——比瞎编好得多

### 4.5 生成（Generation）

```python
answer = llm(prompt)
return {"answer": answer, "sources": [h["metadata"] for h in top_chunks]}
```

> 🔥 **返回 sources（出处）是 RAG 的核心卖点**——用户能点开原文核实，这是纯模型回答给不了的信任感。

## 五、初识：RAG 的常见问题与调优方向

| 问题 | 现象 | 调优 |
|---|---|---|
| 检索不到 | 答案说"资料里没有"，但其实有 | 换 embedding 模型 / 混合检索 / 查询改写 / 调 chunk |
| 检索太多无关内容 | 回答跑偏 | 提高相似度阈值 / 减 top-k / 加 rerank |
| 回答不忠实原文 | 编造资料里没写的内容 | Prompt 约束 + 降低 temperature + 校验引用 |
| 多跳问题答不了 | 需要组合多个文档的信息 | 多轮检索 / Agent 化（ReAct + 检索工具） |
| 更新不同步 | 文档改了，答案还是旧的 | 增量索引 + 版本管理 |

## 六、总结

### 6.1 要点回顾

1. RAG 解决三件事：知识截止、私有知识、幻觉
2. **RAG vs 微调**：知识用 RAG，风格用微调
3. 两条管线：**离线索引（解析→切片→向量化→入库）** + **在线查询（改写→检索→重排→生成）**
4. 切片参数：300~800 字、10~20% 重叠；**embedding 模型入库和查询必须统一**
5. 生成 Prompt 三要素：只依据资料、没有就说没有、**返回出处**
6. 调优主要围绕：检索召回、切片质量、Prompt 约束

### 6.2 自测清单

<details>
<summary>Q1：RAG 的两条管线分别做什么？</summary>

索引管线（离线）：文档解析→切片→向量化→入向量库；查询管线（在线）：问题改写→检索→重排→拼 Prompt→生成。
</details>

<details>
<summary>Q2：为什么 embedding 模型必须统一？</summary>

不同模型生成的向量空间不兼容，入库用 A、查询用 B 会导致相似度计算失效，必须全部重算。
</details>

<details>
<summary>Q3：怎么减少 RAG 的幻觉？</summary>

Prompt 明确"只依据资料回答、没有就说不知道"；降低温度；要求引用出处；检索质量要够（找不到就不硬答）。
</details>

<details>
<summary>Q4：RAG 效果不好，从哪几个方向查？</summary>

先看检索（召回得到吗、排序对吗）→ 再看切片（切得合理吗）→ 再看 Prompt（约束够吗）→ 最后看模型能力。
</details>

### 6.3 面试视角（🔥🔥）

| 面试问法 | 答题要点 |
|---|---|
| RAG 的完整流程？ | 索引：解析/切片/embedding/入库；查询：改写/检索/rerank/拼装/生成 |
| 切片怎么设计？ | 按结构切、300~800 字、10~20% 重叠、父子块兼顾精度与上下文 |
| 怎么提高检索质量？ | 混合检索、rerank、查询改写、优化切片、换更好的 embedding |
| 怎么评估 RAG？ | 检索侧（召回率/命中率）+ 生成侧（忠实度/相关性），人工抽样 + LLM 评审 |
| RAG 和微调怎么配合？ | 先用 RAG 解决知识，风格类需求再加微调；二者可叠加 |
