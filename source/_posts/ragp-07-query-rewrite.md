## 一、初识：为什么原始问题不能直接检索

| 问题类型 | 例子 | 直接检索的后果 |
|---|---|---|
| **口语化** | "那个钱能退不？" | 文档里写的是"退款流程"，语义模型可能能匹配，但召回率打折 |
| **指代** | "它怎么配置？"（上文在说 XR-2000） | "它" 无意义，检索一堆无关内容 |
| **术语不对** | "怎么让机器记住我说的话" | 文档里叫"对话上下文管理" |
| **信息不足** | "多少钱？"（不知道问的什么产品） | 检索结果极其发散 |
| **一题多义** | "报销"（差旅报销 vs 费用报销流程） | 只召回一半相关内容 |

> 一句话：**检索系统只认"和文档表述相近"的文字**——用户的原话往往不是。

## 二、初识：三类改写，解决不同问题

| 类型 | 解决什么 | 做法 |
|---|---|---|
| **① 补全（Contextualize）** | 指代、省略、多轮 | 结合对话历史，把问题补完整 |
| **② 扩展（Expansion）** | 口语 vs 术语、同义表达 | 加同义词、专业术语 |
| **③ 变体（Multi-Query）** | 单一问法召回不全 | 生成 2~4 个不同角度的问法，分别检索 |

### 2.1 ① 补全：指代消解

```text
对话历史：
用户：XR-2000 怎么开机？
助手：长按电源键 3 秒……
用户：那它怎么恢复出厂设置？

改写后：「XR-2000 怎么恢复出厂设置」
```

Prompt 示例：

```text
根据对话历史，把用户当前问题改写成独立、完整、可检索的问题。
要求：补全代词和省略的信息，不要回答问题，只输出改写后的问句。

【历史】
{history}

【当前问题】
{query}
```

> 🔥 这是**多轮对话 RAG 的必要步骤**——没有它，第二轮之后的检索基本都会跑偏。

### 2.2 ② 扩展：把口语翻译成术语

```text
原问题：机器老是记不住我前面说的话
扩展后：对话上下文 记忆 保持 多轮会话 上下文长度
```

实现方式：

- **LLM 改写**：让模型输出"检索友好的关键词式查询"
- **同义词词典**：领域术语表（"退钱 → 退款"）
- **Query Expansion**：从初检结果里提取高频共现词，二次检索

### 2.3 ③ 变体：一个问题问出多个角度

```text
原问题：退款要多久到账？

变体：
1. 退款到账时间
2. 退款处理周期 多久
3. 退回原支付账户 几天
```

每个变体各自检索，结果合并（RRF）——**召回覆盖面显著扩大**。

## 三、初识：HyDE——先编一个"假答案"再检索

**HyDE（Hypothetical Document Embeddings）** 的思路很反直觉：

```text
问题 → 让 LLM 先"编"一段假设性答案 → 用这段答案去检索 → 命中真实文档
```

为什么有效？

| 问题 | 假设答案 | 效果 |
|---|---|---|
| 短文、口语化 | 一段像文档的规范表述 | **和真实文档的向量更接近** |

> 原理：问题（疑问句）和文档（陈述句）在向量空间里本就不够接近；先转成"陈述句的假答案"，就拉近了距离。
>
> ⚠️ 缺点：多一次 LLM 调用（成本/延迟），且假答案可能"编偏"——所以常和原问题一起检索（双路）。

## 四、运用：把改写接进链路

```python
async def rewrite(query: str, history: list) -> list[str]:
    """返回 [原问题, 补全版, 变体1, 变体2]"""
    prompt = REWRITE_PROMPT.format(history=history, query=query)
    result = await structured_llm.ainvoke(prompt)   # 输出 Pydantic 模型

    variants = [query]                              # ⭐ 原问题永远保留
    if result.rewritten:
        variants.append(result.rewritten)
    variants.extend(result.variants[:2])

    return list(dict.fromkeys(variants))            # 去重
```

三个关键设计：

| 设计 | 原因 |
|---|---|
| **保留原问题** | 改写可能改错——原问题作为"保底召回" |
| **变体限 2~4 个** | 每个变体都要检索，多了延迟和成本爆炸 |
| **去重** | 变体可能重复，白跑检索 |

## 五、初识：改写的三个风险与防护

| 风险 | 表现 | 防护 |
|---|---|---|
| **改写跑偏** | 改写后的问题偏离原意 | 保留原问题一起检索；改写结果可回显给用户确认 |
| **成本与延迟** | 每次多一次 LLM 调用 | 简单问题跳过改写（计划里 `need_rewrite=false`）；缓存改写结果 |
| **变体冗余** | 3 个变体检索出同一批文档 | 去重 + RRF 融合（重复的会自然降权） |

### 5.1 什么时候不该改写

| 场景 | 原因 |
|---|---|
| 问题已经很规范（"退款流程是什么"） | 改写收益低 |
| FAQ 精确匹配能命中 | 直接查 FAQ 更快更准 |
| 短查询/关键词型（"XR-2000 重置"） | 关键词检索更合适 |

> 📌 所以改写要由**检索计划**控制（ragp-06 的 `need_rewrite` 字段）——不是每问必改。

## 六、总结

### 6.1 要点回顾

1. 原始问题常常不适合直接检索：口语、指代、术语不符、信息不足
2. 三类改写：**补全（指代/多轮）→ 扩展（口语转术语）→ 变体（Multi-Query 多角度）**
3. **HyDE**：先编假答案再检索——拉近"问题"与"文档"的向量距离
4. 工程要点：**保留原问题**、变体限 2~4 个、去重、RRF 融合
5. 改写不是必做项：由计划控制，简单/规范问题跳过；缓存降本

### 6.2 自测清单

<details>
<summary>Q1：多轮对话为什么必须做指代补全？</summary>

"它怎么办"这类问题脱离历史就没有检索价值；补全成完整问题（XR-2000 怎么恢复出厂设置）才能命中正确文档。
</details>

<details>
<summary>Q2：HyDE 的原理是什么？有什么代价？</summary>

先让 LLM 生成假设性答案，用答案的向量去检索——因为答案与文档的表述更接近；代价是多一次模型调用且有编偏风险，常与原问题双路检索。
</details>

<details>
<summary>Q3：为什么改写后还要保留原问题？</summary>

改写可能偏离原意，保留原问题做保底召回，两路结果融合可降低改写失败的影响。
</details>

<details>
<summary>Q4：什么时候不该做改写？</summary>

问题本身规范、FAQ 能精确匹配、关键词型短查询——此时改写收益低还会增加延迟与成本。
</details>

### 6.3 面试视角（🔥）

| 面试问法 | 答题要点 |
|---|---|
| 查询改写解决什么问题？ | 口语化/指代/术语不符导致召回率低；改写让检索听懂人话 |
| 有哪些改写方式？ | 上下文补全、同义扩展、Multi-Query 变体、HyDE |
| 改写的风险怎么控？ | 保留原问题、限制变体数量、缓存、计划控制是否改写 |
| 多轮对话 RAG 怎么处理？ | 每轮先做指代消解（contextualize），再检索 |
| 怎么衡量改写的收益？ | 对比改写前后的 Recall@K 与最终答案质量（A/B） |
